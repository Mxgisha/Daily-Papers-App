Daily Papers

A phone-native reader for research papers.
Features, stack, architecture, and the path to the app stores.
Prepared from the working repository · 10 commits · ~4,900 lines of Python and ~3,250 lines of TypeScript
Client: Expo SDK 57 / React Native 0.86 / React 19 · Backend tooling: Python 3.14, PostgreSQL 17 + pgvector

1. What the app is

arXiv papers are written for a two-column desktop PDF. Reading one on a phone means pinch-zooming around a page designed for A4, and every existing tool treats mobile as an afterthought. Daily Papers reads the paper as reflowed text instead.

The app lists papers, opens any arXiv paper by id, and renders it as a single column of text sized for the screen. It remembers where you stopped, keeps a shelf of papers you want to come back to, and can read the PDF when arXiv has no HTML version.

96.4%of recent arXiv papers have an HTML full text the app can reflow
100%of papers openable — the remaining ~4% fall back to an in-app PDF reader
0servers to run; the app has no backend of its own

Who it is for

Someone who wants to keep up with a field on their phone — on a commute, in a queue — rather than at a desk. That is a different job from reference management, which is why the app does not try to be a library.

What it deliberately is not

Not a replacement for Zotero or Mendeley: no citation management, no annotation, no PDF library. Not a search engine: it is a reader that can search. Not a social network.

2. Features

Finding papers

FeatureWhat it does
Bundled paper list 300 recent papers ship inside the app, so the list works with no network and opens instantly. Regenerated from the project database by a script.
Search all of arXiv Queries the arXiv API across the whole corpus rather than only the bundled snapshot. Runs on submit rather than per keystroke, so typing stays instant and the API is not hammered.
Topic filter arXiv categories grouped into labels a person actually uses — ML / AI, CS, Math, Physics, Biology, Statistics, Signals, Economics — with counts, so empty topics hide themselves.
Open any arXiv id Paste an id and open it. Handles both modern ids (2610.13948) and the older slash form (math.GT/0309136), which otherwise breaks routing.
Paper of the day Today's most-upvoted paper from Hugging Face Daily Papers — a real, human hotness signal. See the note below on why citations are not used.
On "hot right now". Citations are useless for this: all 300 bundled papers are from a single day and exactly one has a citation. The app collects no read counts either, so "most read" is unavailable and would be dishonest to fake. Hugging Face upvotes are a genuine daily signal, so that is what the paper of the day uses. When it is unreachable the app falls back to a rotating local pick — and labels it differently, because that fallback is not popularity.

Reading

FeatureWhat it does
Reflowed HTML reading arXiv's own full text, with the site chrome removed and the article re-laid into one column: comfortable measure, resizable text, native scrolling.
In-app PDF reader For the ~4% of papers with no HTML, the PDF is rendered inside the app by PDF.js. No native module, so the app still runs in Expo Go.
Reading position memory Reopening a paper returns you to where you stopped, on both the HTML and PDF paths.
Figures load lazily Opening a long paper used to pull every figure at once — 28 MB against 388 KB of text. Figures now load only as they come near the screen.
No sideways scrolling Footnotes, unparsed formulas, wide tables and long URLs were each dragging the page wider than the screen. Each is contained or scrolls within itself.

Keeping track

FeatureWhat it does
Save for later Star any paper from the list or from inside the reader. Saved papers keep their own title, authors and abstract, so the shelf renders with no network.
Saved tab A second tab listing everything you kept, with a live count in the tab label.
Light / dark theme Explicitly chosen, never automatic — the app chrome, the article and the tab bar all follow the choice together.

3. The stack, and why

Client (what a user installs)

PieceWhy this one
Expo SDK 57
React Native 0.86, React 19		 One codebase for iOS, Android and web. Expo Go means the app can be tested on a real phone without a build step, which is why native modules were avoided throughout.
TypeScript 7 Types are the cheapest test there is. The reader's position logic and the storage shapes are the kind of thing that fails silently at runtime.
expo-router File-based routing with tabs. The reader sits outside the tab group so it opens full screen.
react-native-webview Carries both renderers — the reflowed HTML and the PDF.js viewer. A WebView for one screen is a deliberate choice, not a wrapped website: the markup is deeply nested HTML with tables and native MathML, and parsing that into native components would be a large amount of work with no good answer for equations.
AsyncStorage Saved papers, reading positions and a metadata cache. Small key–value data; a database would be overkill.
PDF.js 3.11.174
classic UMD build, from CDN		 Renders PDFs with no native code. The classic build rather than v4's ESM one because module loading from a null-origin document is exactly what WebViews differ on.
fast-xml-parser arXiv's API returns Atom XML, and React Native has no DOMParser.
The app has no backend. Every content path is either a bundled asset or a direct request from the phone to arXiv. There is nothing to deploy, nothing to pay for, and nothing to go down.

Tooling (developer machine, never shipped)

PieceWhy this one
Python 3.14 The whole data path — crawling, enriching, embedding, bundling — is one language.
PostgreSQL 17 + pgvector Paper metadata and embeddings in one store, with ANN search. Docker Compose, host port 5433.

Why the reading position is stored as two numbers

A scroll offset in pixels is meaningless once the text reflows, the font size changes or the theme switches. A pure fraction of the document drifts too, because lazy figures keep growing the page after load. So the app stores both:

  • fraction — how far through, as 0–1.
  • anchor — the index of the topmost visible block element, or page for a PDF.

On reopen the anchor is scrolled into view and the restore is re-applied for a few seconds while the document settles, stopping the moment the reader touches the screen. That is what turned an intermittent restore into a reliable one.

Why saves keep their own metadata

A paper opened from arXiv search is not in the bundled list. If a save stored only an id, the Saved tab would have nothing to render without a network round trip — and a paper opened cold from a pasted id would be saved under its number rather than its name. So saved entries carry their title, authors and abstract, and anything that appears on screen is cached so a later cold open still has a real title.

Being precise about this matters more than a feature list.

Verified by running it

Topic picker and paper of the dayChips with counts; 79 upvotes fetched live
TypeScript typechecks, Android bundle buildstsc --noEmit; expo export

Not verified — needs your phone

  • The star tap and the tab press. Automated input could not drive these; the storage and render paths are verified instead, but the tap handlers themselves are unproven.
  • PDF.js on a real device. The web target uses the browser's own PDF viewer, so the PDF.js path only runs on native.
  • Reading-position restore on a device. The anchor logic is verified in principle; real scrolling behaviour has not been measured on hardware.
  • Math rendering. arXiv serves native MathML, whose quality depends on the device having a maths font. Every formula embeds its original LaTeX, so bundling KaTeX is the fix if equations look wrong.

Known rough edges

  • PDF.js loads from a CDN. First use needs a network round trip for ~1.4 MB. Bundling it with the app would remove that, at the cost of repo size.
  • Reading position has no visible UI. It restores silently; there is no "back to top" or progress indicator outside the PDF path.
  • The bundled list is a snapshot. 300 papers from one day, rebuilt by hand. There is no refresh, so it ages.
  • Search needs a network and hits arXiv's API directly, so it is subject to their rate limits.

7. Ideas for what is next

Closest to done — small and high value

  • A "back to top" and a progress indicator in the reader. The position is already known; showing it costs almost nothing.
  • Collections — group saves into folders ("read for the survey", "thesis"). The storage layer already holds a list; this adds a tag.
  • Mark as read, and a reading-history view. The position data already implies it.
  • Share a paper — the app deals in arXiv ids, which are already good links.
  • Export citations to BibTeX, or push a paper into Zotero.

Substantial, and clearly wanted

  • Offline reading. Save the article HTML and its figures for a flight. The lazy-figure work is most of the plumbing already.
  • Highlights and notes. The hardest part is text selection inside the WebView, which is why it is not in the MVP.
  • Daily digest notifications — a local scheduled notification, no server needed.
  • KaTeX maths rendering to remove the device-font dependency.
  • Figure downscaling — figures are the largest data cost in the app by a wide margin.
  • Text-to-speech, so a paper can be listened to.

The big one: recommendations

This is already built and verified, and deliberately switched off. Embeddings for the corpus, on-device scoring, MMR diversification and exploration all exist under src/core/, cross-checked against a Python reference implementation. What it lacks is a reason to trust it: with 300 papers from one day and no usage data, a "recommended" feed would be a guess dressed up as a feature.

The honest sequence is: ship the reader, collect what people actually read, then turn it on. Which leads to the one piece of infrastructure worth adding.

The one thing worth adding next

Usage telemetry, opt-in. Every feature in this document is currently blind — nobody knows which papers get opened, where readers stop, or what gets saved. The reading-position and saved-paper data already exists locally and would answer those questions. A small, clearly consented, privacy-respecting upload would make every future decision measurable instead of speculative, and it is the prerequisite for recommendations being anything more than a plausible guess.

8. Getting it into the app stores

What is required before anything else

RequirementNotes
A native buildExpo Go is a development shell and cannot be submitted. A standalone build is produced by EAS Build — a cloud service, so no Mac is required for iOS. This is the main reason EAS exists in this stack.
Apple Developer Program~$99/year. Needed for TestFlight and the App Store.
Google Play account~$25 once.
App identityBundle identifier (already app.dailypapers), app name, icon, splash screen.
Privacy policyRequired by both stores. A URL is enough.
Store listingScreenshots per device size, description, keywords, category.

Fees and review policies change — confirm current figures with Apple and Google before budgeting.

The path, in order

  1. Freeze scope. Decide what "1.0" means. The reader, search, saves and position memory are a coherent product on their own.
  2. Add the finishing pieces the stores require: icon and splash, a privacy policy, and — on iOS — Sign in with Apple if any other sign-in is offered (there is currently no sign-in at all, which is the simplest position to be in).
  3. Configure EAS. An eas.json with development, preview and production profiles. The preview profile produces a shareable Android APK; production produces the .aab and .ipa the stores want.
  4. Test on real hardware. Everything in section 6 marked unverified gets closed here. Use a preview build rather than Expo Go — it is the same binary the stores would receive.
  5. Beta first. TestFlight on iOS, an internal or closed track on Google Play. Real readers on real papers, for a couple of weeks.
  6. Android, then iOS. Android review is faster and the account is cheaper, so it makes a better first submission. Note that personal Google Play accounts created recently must run a closed test with a minimum number of testers for a minimum period before applying for production — check the current rule, but budget time for it.
  7. Submit. Expect at least one rejection round. Both stores give a reason and a route to appeal or resubmit.
  8. Over-the-air updates afterwards. JS-only changes can ship through EAS Update without a store review, which shortens the loop considerably for a reader that mostly renders text.

The three rejection risks worth planning for

RiskHow to avoid it
iOS 4.2 — minimum functionality Aimed at apps that are just a website in a shell. This app is not: it reflows content, stores state on the device, works offline for its list, and has an in-app PDF reader. Keep it that way, and be ready to explain what is native.
Content rights The app links to arXiv and does not rehost PDFs or articles. Keep it that way; the moment files are mirrored in bulk, licensing becomes a real question.
Privacy declarations Both stores require a data-safety / privacy questionnaire. Today the honest answer is that everything stays on the device. That answer changes the day telemetry is added — which is a reason to design it opt-in and minimal from the start.

A realistic sequence

StageWork
1. PolishIcon, splash, empty states, error copy, offline behaviour. Small but visible.
2. Device passClose every "not verified" item on real hardware; fix what it surfaces.
3. PackagingEAS profiles, keystore, signing credentials, privacy policy page.
4. BetaTestFlight and a Play closed track; gather real reading feedback.
5. LaunchAndroid first, then iOS. Plan for one rejection round.
6. IterateEAS Update for fast fixes; then collections, offline reading, and eventually recommendations.

9. Appendix — running it

Run the app

cd mobile
npm install
npm start                 # scan the QR code with Expo Go

npm run typecheck         # TypeScript, app and tests
npm test                  # cross-checks against the Python reference

Verify the reader in a browser

cd mobile
npx expo export --platform web --output-dir ../dist-web
python3 harness/run_reader_mvp.py --web ../dist-web --out ../reports/reader-mvp

Exports the app, serves it, drives a headless Chromium at an emulated iPhone 14 viewport, screenshots every screen and writes report.json.

Rebuild the bundled paper list

docker compose up -d postgres
.venv/bin/python -m ingest init-db
.venv/bin/python -m ingest crawl --per-category 100
.venv/bin/python -m ingest embed
.venv/bin/python mobile/scripts/export_papers.py --out mobile/assets/papers.json --limit 300

Regenerate the reader stylesheet

cd mobile && npm run gen:reader-css

The app's reader CSS is generated from reader/static/reader.css so the verified stylesheet and the shipped one cannot drift apart. Edit the spike stylesheet, never the generated file.

A note for whoever works on this next. Three separate bugs in this project were found by running the software rather than reading it: a footnote style that made pages twice the width of the phone, a title that saved as a number, and a position that restored to the wrong place. The verification harness exists because compiling proves almost nothing about a reader. Keep using it.
